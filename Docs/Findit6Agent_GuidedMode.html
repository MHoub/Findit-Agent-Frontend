Guided Mode

Guided Mode turns one user question into a controlled sequence of smaller AI tasks. It is designed especially for local or smaller language models that are not reliable enough to plan and execute a complete autonomous research strategy on their own.

Instead of asking one model to manage the entire research process, Guided Mode breaks query construction, semantic ranking, document evaluation and synthesis into carefully defined stages. Each stage receives only the information and instruction it needs.

This page is more than documentation.
It also serves as a direct reference to the instruction files that control Guided Mode. The linked Markdown files are the actual working instructions used by Findit6Agent during research. You can open them directly from this page and, where appropriate, adapt them to your own archive and workflow.

Most core instruction files should normally remain unchanged; Agent_User_Rules.md is specifically intended for your own archive-specific rules and additions.

Why Guided Mode works in separate steps

Building a useful deterministic full-text query is more complex than it first appears. The goal is to retrieve as many relevant files as possible without producing an excessive number of irrelevant hits.

For this reason, query construction and later document evaluation are divided into separate AI tasks. Especially with local models, context windows may be limited while the documents to be evaluated can be large. Guided Mode therefore processes most stages independently and without conversation history unless a later stage explicitly requires memory.

User question→ Query construction→ Findit6→ Reranker→ Document excerpts→ Synthesis

Guided Mode settings

When connecting a model, two preset values can be adjusted.

Maximum Excerpt Length defines the maximum amount of text that may be supplied to the model in an individual excerpt-processing step. Models with smaller context windows may require a lower value.

Duplicate Threshold defines how similar two files must be according to Findit6Agent's internal similarity calculation before one of them is treated as a duplicate and excluded from further evaluation. The default value of 80 is tuned to identify very close duplicates while preserving documents with substantial differences. The value is a similarity score, not a literal percentage of identical text.

Moods: different settings for different tasks

Local models can behave very differently depending on the task and on inference parameters. Findit6Agent calls these task-specific presets Moods.

A narrowly defined logical task may work best with little or no reasoning, low temperature and tightly constrained sampling. A broader or more creative task may benefit from more reasoning and a wider range of possible continuations.

Each Guided Mode step therefore selects an appropriate Mood. The selected Mood is defined in the corresponding Markdown instruction. The Mood settings themselves can be adjusted in Findit6Agent.ini.

Markdown instructions

For every processing step, the AI receives a dedicated Markdown instruction file into which Findit6Agent inserts the information required for that stage.

These Markdown files can be edited directly and are the main way to fine-tune Guided Mode. Small wording changes can have unexpectedly large effects, so modifications should be made carefully.

A clean copy of the original Markdown files is kept in the Findit6Agent program directory so the default behaviour can always be restored.

Step 0 Prepare the user question Mood: LogicalSmall

chunk_Query_0.md

If necessary, the AI performs a light spelling correction, determines the language used by the user and detects any time restriction requested in the question, for example documents from the last four years.

This step normally takes only a few seconds.

Step 1 Identify the core entity or entities Mood: LogicalLarge

chunk_Query_1.md

Most questions contain one core entity that must appear in every document capable of answering the question. In rare cases there may be two equally important core entities that have to be treated separately.

Example: For dogs and cats, what is documented about their paws and claws?
The core entities are dogs OR cats. Relevant documents may concern either one.

Depending on the complexity of the question, a smaller local model may need some time to make this decision reliably.

Step 1b Determine the logical relationship between multiple core entities Mood: LogicalSmall

chunk_Query_1b.md

If two equally important core entities are found, the AI decides whether they are likely to occur in different documents or whether both must be discussed together in the same document.

Alternative: “What do we know about the paws of dogs and cats?” The entities can be searched as alternatives.

Intersection: “Why do dogs and cats rarely get along well?” Both entities are part of the same relationship and normally need to occur together.

Step 2 Identify relevant aspects Mood: LogicalSmall

chunk_Query_2.md

Most questions ask for specific details about the core entity. At this stage the AI identifies the relevant aspects as plain terms without yet deciding how they should be combined logically.

Step 3 Determine the logical relationship between aspects Mood: PreciseLarge

chunk_Query_3.md

The AI decides whether the aspects must be connected by AND or OR.

Example:
(dogs OR cats) AND (paws OR claws)
At least one core entity and at least one relevant aspect should occur in every useful document.

This logical stage can require substantial reasoning for complex questions, especially when smaller local models are used.

Step 4 Remove soft aspects Mood: PreciseLarge

chunk_Query_4.md

Some aspects are poor full-text search terms even though they are important to the meaning of the question.

For example, if the user asks for a person's profession, the word profession itself may never appear in documents that instead say the person is a carpenter, lawyer or researcher.

Such soft aspects are therefore removed from the deterministic search expression. Findit6 can first retrieve documents about the person; the semantic reranker and later AI analysis can then identify which files actually contain the requested professional information.

Step 5 Apply user rules Mood: Precise

chunk_Query_UserRules.md

You know your own documents better than the software does. If recurring information in your archive follows predictable patterns, custom rules can help the AI build more effective searches.

Example: A mobile phone number may be labelled mobile, cell or phone - or may not be labelled at all. In Germany, mobile numbers normally begin with 015, 016 or 017.

A user rule can therefore treat 015* OR 016* OR 017* as strong evidence for a mobile phone number.

The supplied Markdown contains example rules and can be adapted to the characteristics of your own archive.

Step 6 Truncate words to useful stems Mood: Precise

chunk_Query_6.md chunk_Query_6D.md

Findit6 searches exact character sequences. A search for battery would not automatically find batteries. The AI therefore reduces suitable words to the shortest useful stem, for example batter*. An occasional false positive can later be removed by the semantic reranker.

This stage uses a hybrid linguistic truncation method developed independently for Findit6Agent by Michael Houben in 2026. It combines context-sensitive LLM-derived morphological and derivational word forms with deterministic common-prefix truncation, a minimum-prefix safety threshold and an OR fallback when no sufficiently safe common prefix exists.

Step 7 Possible leading wildcard Mood: Precise

chunk_Query_7.md chunk_Query_7D.md

The AI decides whether a leading wildcard is useful. For example, *book* may also find notebook, textbook, handbook or bookshelf. But a pattern such as *art* could match many unrelated words.

A leading wildcard is therefore added only when it is likely to improve recall without creating excessive noise. This optimization is language-dependent and currently uses separate English and German instruction files.

Step 8 Final query optimization Mood: Reasoning

chunk_Query_8.md chunk_Query_8D.md

The AI may add close synonyms with the same intended meaning. For example, a search for car may also need automobile or vehicle.

This optimization is language-dependent and currently uses separate English and German instruction files.

Findit6 starts the full-text search

The finished query is now sent to Findit6. On suitable hardware, Findit6 can scan roughly 100 GB of data per minute. While the full-text search is running, the AI can already prepare the next stage.

Build the reranker question Mood: Precise

chunk_Identify_Questions.md

Findit6 retrieves every file matching the deterministic query, but it has no semantic understanding and cannot decide whether a matching document actually answers the user's question. Reading every hit with the AI would be inefficient.

The AI therefore converts the user's information need into one or more concise questions for the local semantic reranker.

Example: “Which products does Example Company manufacture, and which of them present a swallowing hazard?”
General product information and safety reports may live in very different files. Separate reranker questions can improve retrieval quality.

Reranking the Findit6 results

When the Findit6 search is finished, the result list can be opened directly from the protocol.

The local semantic reranker scores the found files according to their likely relevance to the current reranker question. On a typical consumer GPU, roughly 100 files per minute may be evaluated. High-end systems can be faster; laptops may be substantially slower.

The Session Workspace contains the reranked result list sorted by relevance score.

Read the most relevant files Mood: Precise

chunk_06_ExcerptLong.md chunk_06_ExcerptMed.md chunk_06_ExcerptShort.md

The AI processes the highest-ranked files one after another. A local AI with a limited context window extracts the relevant passages and collects them in an excerpt file for later synthesis. These files are stored in the Session Workspace, for example as excerpt_xx.txt.

At the end of the search-run you will find a file xyz_excerpt.txt within the Session folder. It will contain all excerpts the agent produced

Small, medium-sized and very large files are handled slightly differently for efficiency. Separate Markdown instructions are therefore used for different file sizes and for local versus large external models. These files usually require little or no customization.

Synthesis - build the final answer Mood: Precise

chunk_8_Synthesis.md chunk_8_SynthesisBigMod.md

The local AI receives the collected excerpts. A large external AI may already have the relevant material in its working context. The synthesis instruction asks the AI to answer the current question from this evidence.

If several separate information needs were identified earlier, the excerpt and synthesis stages are repeated for each one. The synthesis instructions also define how conflicting information should be handled and how direct source-file references should be added whenever possible.

A complete Guided Mode search

At this point the Guided Mode workflow is complete. The final stages - reading relevant files and synthesizing the answer - may run several times when the original user question was split into multiple independent information needs.

The linked Markdown files allow the workflow to be fine-tuned in considerable detail. Please change them carefully: small modifications can sometimes have large and unexpected effects. The original versions remain available in the Findit6Agent program directory so the default configuration can always be restored.

Statistical research

The Guided Mode described on this page is currently optimized for knowledge-oriented research: identify relevant documents, rank them semantically, extract useful evidence and synthesize an answer.

Systematic statistical research - for example counting, classifying, deduplicating or aggregating a complete document population - uses a different research contract. This capability is currently implemented in Agent Mode through its dedicated Statistic research workflow.

A future Guided statistical workflow could reuse the same underlying ideas while dividing the work into smaller local-model-friendly stages. In particular, the persistent Ledger architecture provides a natural basis for collecting compact task-specific facts from many documents before deterministic classification or calculation. This is not yet part of the Guided workflow described above.
